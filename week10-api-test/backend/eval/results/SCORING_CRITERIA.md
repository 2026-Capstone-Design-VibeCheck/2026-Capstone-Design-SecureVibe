# SecureVibe 모델 평가 채점 기준

총 3 카테고리, 9개 항목, 모두 **1~5점 척도**.

---

## 1. 정확성 (Security Accuracy)

### 1-1. True Positive 수정 품질 (1~5점) — 취약 샘플 7개에 적용

실제 취약점을 **올바르게** 수정했는가?

| 점수 | 기준 |
|---|---|
| **5** | 업계 표준 방어 적용 (예: SQL → parameterized query, MD5 → bcrypt/PBKDF2, Path Traversal → realpath + 컨테인먼트 검증) |
| **4** | 작동은 하지만 최소 수준 (예: Path Traversal에 basename만 사용 — flat dir에선 안전하지만 일반성 부족) |
| **3** | 일부 방어만 적용, 우회 가능 (예: MD5 → SHA-256 단순 교체, 여전히 빠른 해시이므로 부적절 / normpath만 사용해 `/var/app/uploadsX` 같은 prefix 우회 허용) |
| **2** | 주장과 코드 불일치 — "고쳤다"고 했는데 실제 코드엔 취약점 잔존 (예: gpt-4o-mini가 sample 10에서 "PII 출력 안 함"이라 했지만 `print(result[2])` 그대로) |
| **1** | 수정 자체가 잘못됨 |

### 1-2. 코드 무결성 (1~5점) — 취약 샘플 7개에 적용

기존 비즈니스 로직(함수 시그니처·변수명·동작)을 훼손하지 않았는가?

| 점수 | 기준 |
|---|---|
| **5** | 함수 시그니처·변수명·반환값 완전 유지 |
| **4** | 거의 유지하지만 사소한 변경 (예: 코드는 PBKDF2지만 주석엔 "bcrypt"라고 잘못 명시) |
| **3** | 일부 시그니처/동작 변경 |
| **2~1** | 함수 인터페이스가 바뀌어 호출부 수정 필요 |

### 1-3. False Positive 필터링 (1~5점) — 안전 샘플 2개에만 적용

이미 안전한 코드를 **"수정 불필요"라고 인지**하는가?

| 점수 | 기준 |
|---|---|
| **5** | 명시적으로 "이미 안전, Semgrep 오탐"이라고 판단 + 코드 그대로 또는 코멘트만 추가 |
| **4** | 안전성 인지하지만 일부 가독성 개선만 (수정 없음에 가까움) |
| **3** | "이미 안전"이라고 일부 인지하면서도 무의미한 리팩토링 동반 (예: deepseek `check=True` 추가, llama `run` → `Popen`) |
| **2** | FP 인지 실패, 무의미한 수정 추가 (예: haiku의 `connection.close()` 추가, gpt-4o-mini의 `["...""] + [action]` 무의미 변경) |
| **1** | FP 인지 실패 + 부작용 도입 (예: gpt-4o-mini의 `isdigit()` 변경으로 음수 ID 거부 — 원본 `int()`보다 좁은 입력 허용) |

## 2. 사용성 (UX/Education) — 모델당 1회 종합 평가

### 2-1. 설명 난이도 (입문자 이해도, 1~5점)

| 점수 | 기준 |
|---|---|
| **5** | "왜 위험한지"를 비전공자도 이해할 한국어로 풀어줌. 코드 변경 동기 명확 |
| **4** | 짧지만 명확, 핵심은 전달 |
| **3** | 기능적이지만 일반적·짧음, 초보자에겐 불충분 |
| **2~1** | 전문 용어 나열, 설명 빈약 |

### 2-2. 요약의 핵심 ("왜/어떻게" 한눈 파악, 1~5점)

한줄 요약이 (1) 무엇을 바꿨고 (2) 왜 안전해졌는지를 압축했는가?

| 점수 | 기준 |
|---|---|
| **5** | 무엇을 바꿨고 왜 안전해졌는지 한 줄에 모두 압축 |
| **4** | 핵심 전달, 일부 사례에서 짧음 |
| **3** | 매우 간결, "왜"가 빠진 경우 있음 |

### 2-3. 가독성 (1~5점)

| 점수 | 기준 |
|---|---|
| **5** | ` ```python ` 처럼 언어 명시, 코드 블록 1개, 한줄 요약 일관 형식 |
| **4** | 거의 일관, 사소한 차이 |
| **3** | ` ``` ` 언어 누락 빈번, "주석:" 같은 추가 섹션 일탈 |

## 3. 운영 적합성 (Operational Fitness) — 자동 산정

세 메트릭 합산, **15점 만점**. 구현은 [metrics.py](metrics.py) 참조.

### 3-1. 평균 지연시간 → 1~5점 환산 ([metrics.py:65-78](metrics.py#L65))

| 평균 지연 | 점수 |
|---|---|
| < 2.0s | 5 |
| < 3.5s | 4 |
| < 5.0s | 3 |
| < 7.0s | 2 |
| ≥ 7.0s | 1 |

→ 체크리스트의 "5초 이내 권장" 기준 반영

### 3-2. 구조 준수율 → 1~5점 환산 ([metrics.py:81-91](metrics.py#L81))

정규식으로 (1) 코드 블록 존재, (2) "한줄 요약:" 포함 자동 체크.

| 준수율 | 점수 |
|---|---|
| ≥ 95% | 5 |
| ≥ 85% | 4 |
| ≥ 70% | 3 |
| ≥ 50% | 2 |
| < 50% | 1 |

### 3-3. 일관성 → 1~5점 환산 ([metrics.py:94-104](metrics.py#L94))

Temperature 0.1로 동일 입력 **3회** 호출 → 응답 간 Jaccard 유사도 평균.

| Jaccard | 점수 |
|---|---|
| ≥ 0.80 | 5 |
| ≥ 0.65 | 4 |
| ≥ 0.50 | 3 |
| ≥ 0.35 | 2 |
| < 0.35 | 1 |

## 4. 총점 산정

```
정확성 합계 = TP수정×7 + 코드무결성×7 + FP필터링×2   (최대 80점, 풀 10샘플 기준 90점)
사용성 합계 = 설명 + 요약 + 가독성                  (최대 15점)
운영 적합성 = 지연환산 + 구조환산 + 일관성환산        (최대 15점)
─────────────────────────────────────────────────────
총점 = 정확성 + 사용성 + 운영                       (최대 120점)
```

## 5. 채점 데이터 출처

- 점수는 [auto_score.py:25-180](auto_score.py#L25)에 `SCORES` dict로 모두 박혀 있어 **재현 가능**
- 각 점수는 [results/_compare_samples.txt](results/_compare_samples.txt)에 모인 raw 응답을 평가자가 직접 읽고 부여
- 운영 점수는 [run_eval.py](run_eval.py)가 실제 호출하며 측정한 latency·token·response_text를 [metrics.py](metrics.py)가 자동 계산
- 데이터셋 10개 샘플은 [samples/](samples/) (TP 7개 + FP 2개 + main.py 실제 코드 1개)

## 6. 가중치 변경 시

기본은 단순 합산. 다른 가중치를 적용하고 싶으면 `auto_score.py:render_report`에서:

```python
weighted = (
    s['accuracy_sum'] / s['accuracy_max'] * 0.50   # 정확성 50%
    + s['usability_sum'] / 15 * 0.25                # 사용성 25%
    + s['ops'] / 15 * 0.25                          # 운영 25%
)
```

예시 권장 가중치:
- **`/suggest-fix` 평가**: 정확성 60% + 사용성 20% + 운영 20% (정확성 최우선)
- **`/chat` 평가**: 사용성 50% + 정확성 30% + 운영 20% (설명 풍부함이 중요)
